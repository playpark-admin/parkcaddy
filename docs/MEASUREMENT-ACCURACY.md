# ParkCaddy 지면 측정 원리와 정확도

2.2 자동 스캔 기준, 2026-09-27. 구현된 관측 조건, 수학 모델, 검증되지 않은 실제 성능을 구분합니다. **실물 Android 브라우저에서 현재 WebXR 전체 흐름을 실행한 검증과 야외 측량 정확도 검증은 아직 완료하지 않았습니다.** 시험 결과와 빌드 상태는 [VALIDATION.md](VALIDATION.md)를 따릅니다.

## 1. 현재 계산하는 값

웹의 현행 계산은 `webxr-scan.mjs`와 `terrain-core.mjs`가 담당합니다. WebXR에서 얻은 CPU 접근 깊이와 카메라 자세를 같은 세계좌표로 변환하고 실제 관측된 지면 점의 상대 높이와 수평거리를 계산합니다. 사진 한 장이나 휴대전화 기울기를 지형 높이로 바꾸지 않습니다.

```text
정규화 화면 좌표 (u,v)
ray = inverseProjection × [2u−1, 1−2v, −1, 1]  (동차좌표 나눗셈 후)
p_camera = ray × depth_m / (−ray.z)
p_world = worldFromView × [p_camera, 1]

상대 높이 Δh = y_target − y_reference
웹 수평거리 d = √((x_target − x_camera)² + (z_target − z_camera)²)
```

WebXR 깊이는 카메라 평면으로부터의 축 방향 거리이며 비스듬한 광선 길이가 아닙니다. `getDepthInMeters(u,v)`는 정규화된 view 좌표를 받고 내부에서 깊이 버퍼 좌표 변환을 적용하므로 같은 변환을 다시 곱하지 않습니다. 깊이 0은 유효한 지면 0 m가 아니라 미확정 깊이입니다. [W3C 깊이 좌표와 API](https://www.w3.org/TR/webxr-depth-sensing-1/#xrcpudepthinformation), [깊이의 물리적 의미](https://www.w3.org/TR/webxr-depth-sensing-1/#interpreting-the-results)

`raw` 깊이를 요청하지만 브라우저가 그 요청을 그대로 제공한다는 보장은 없습니다. 실제 제공된 `depthType`과 `depthDataFormat`을 진단에 기록합니다. CPU 접근 가능 여부는 계산 경로이고 정확도 등급이 아닙니다. Android 앱의 Raw Depth confidence와 동일한 픽셀 신뢰도 채널이 웹에 있다고 가정하지 않습니다. [W3C 깊이 세션 설정](https://www.w3.org/TR/webxr-depth-sensing-1/#session-configuration)

Android 앱은 ARCore Raw Depth, iOS 앱은 지원 기기의 sceneDepth를 이용합니다. Android의 0.4–2.3 m 기준 후보 높이 조건은 내부 필터이며 사용자가 렌즈 높이를 입력하는 보정값이 아닙니다. 이 조건을 통과하는 책상·벤치도 있을 수 있으므로 실제 발 앞 지면인지 확인해야 합니다. 각 플랫폼의 좌표계·단위·거리 기준은 구현에 맞게 해석해야 하며 웹의 카메라 기준 수평거리와 다른 기준점의 거리를 무조건 같은 값으로 합치지 않습니다.

## 2. 자동 기준점과 기본 높이 설정

웹은 중앙 깊이점과 수평 지면 hit-test가 맞는지 확인하고 반복 관측으로 기준 지면을 잡습니다. 현재 기준 후보 조건은 다음과 같습니다.

- 카메라와 후보 지면의 실제 높이 차가 설정 범위 안에 있을 것. 기본은 0.4–2.3 m.
- 관찰 범위 안의 점이며, hit-test 지면과 깊이점의 높이 차가 12 cm 미만일 것.
- hit-test 법선 및 인접 깊이점의 법선이 수평 지면 후보 조건을 만족할 것.
- 서로 다른 깊이 버퍼에서 5회 이상, 400 ms 이상 관측하고 높이 MAD가 1.5 cm 이하일 것. 최근 2초·수평 35 cm·높이 차 4.5 cm 안의 후보를 비교하며 최대 9개를 유지합니다.

이 조건은 책상·벽·먼 물체를 지면으로 잘못 잡는 일을 줄이기 위한 휴리스틱입니다. 잔디 표면이나 평평한 물체를 의미적으로 완전히 구분하지 못합니다. **기본 높이 설정은 후보 필터이며 입력값을 깊이에 곱하거나 미터 척도를 보정하지 않습니다.** 높이 범위를 좁게 입력해도 센서의 물리적 정확도가 좋아지는 것은 아닙니다.

## 3. 웹 반복 관측과 표시 조건

| 조건 | 현행 값 | 의미 |
| --- | --- | --- |
| 세계좌표 셀 | 25 cm | 가까운 관측을 같은 셀로 묶음 |
| 최소 채택 표본 | 셀당 7개 | 같은 깊이 프레임의 여러 픽셀을 한 표본으로 집계 |
| 관측 시간 폭 | 1.2초 이상 | 실제 첫/마지막 채택 표본의 시각 차 |
| 카메라 이동폭 | 수평 8 cm 이상 | 카메라 x/z 위치 차. 회전만으로 충족되지 않음 |

| 최근성 | 마지막 채택 관측 1.2초 이내 | 오래된 점은 표시에서 제외 |

| 주요 숫자 표시 | 안정 셀 ≥ 9개, 유효 인접 연결 ≥ 8개 | 추가로 화면 안에 9개 이상, 중앙 근처 목표 관측점 필요 |

깊이는 약 125 ms 이상 간격으로 처리합니다. 실제 버퍼의 fingerprint와 프레임 식별로 반복 반환된 버퍼가 새 관측으로 누적되는 일을 줄입니다. 다른 fingerprint도 독립적인 센서 오차라는 뜻은 아니며 fingerprint 자체도 암호학적 관측 증명이 아닙니다.

시간 이상값은 `max(1.5 cm, 3 × 1.4826 × MAD)`보다 중앙값에서 멀리 떨어진 표본을 제외하는 방식으로 거릅니다. 실제 점의 x/y/z 중앙값을 보존하고, 셀 중심의 가상 높이로 치환하지 않습니다. 따라서 25 cm 셀은 분류 해상도이며 웹 좌표 오차의 ±17.7 cm 상한이라는 뜻이 아닙니다.

선은 실제 관측된 인접 셀끼리만 잇습니다. 높이 차가 18 cm를 넘거나 수평 간격이 셀 폭의 1.7배를 넘으면 연결하지 않습니다. 미측정 셀을 가로질러 높이를 보간하지 않습니다. 안정 셀과 연결 수 조건은 관측 범위 조건이며 구장 전체를 측량했다는 뜻은 아닙니다. 먼저 안정된 점은 격자에 반영하고, 주요 중앙 숫자는 별도 준비 조건을 충족할 때 표시합니다.

진행률에는 표본 수·시간 폭·시점 이동·관측 범위 조건을 사용합니다. 시간만 흐른다고 100%가 되지 않으며, 100%도 정확도 확률이 아닙니다. 깊이가 없거나 추적을 잃으면 숫자를 숨기고 구체적 안내를 표시합니다. Android/iOS의 기본 측정 버튼은 제거했지만 웹은 세션을 여는 사용자 터치가 필요합니다. [WebXR 세션 시작 절차](https://www.w3.org/TR/webxr/#application-flow)

## 4. 왜 반복만으로 최고 정밀도를 보장할 수 없는가

작은 MAD는 비슷한 값이 반복되었다는 뜻입니다. 깊이 센서의 공통 편향, 카메라 내부/외부 보정 오류, 기준 지면 오류, AR 자세 드리프트, 잔디 윗면의 편향은 같은 방향으로 남을 수 있습니다. 필터 통과나 cm 단위 표시로 실제 cm 정확도를 보장하지 않습니다.

각 관측의 분산이 σ²이고 모든 다른 표본 쌍의 상관이 동일한 ρ라는 모델에서:

```text
Var(mean) = σ² [1 + (N − 1)ρ] / N
N_eff = N / [1 + (N − 1)ρ]
```

이는 특정 상관 모델의 수학적 결과이며 앱이 ρ를 실측했다는 뜻은 아닙니다. N=100, ρ=0.1이면 N_eff≈9.17이고 표준편차 비율은 약 0.330입니다. 독립 표본의 0.1배 감소를 주장할 수 없습니다. 공통 편향은 평균으로 없어지지 않고 MAD도 편향 보정을 대신하지 않습니다.

미터 깊이와 카메라 자세의 오차는 함께 상대 높이에 영향을 줍니다.

```text
p_world = R · p_camera + t
Δh = upᵀ (p_target − p_reference)
Σ_difference = Σ_target + Σ_reference
             − Cov(target,reference) − Cov(reference,target)
```

공분산을 알 때 적용하는 식이며 sensor confidence를 공분산으로 바꾸어 넣지 않습니다. 작은 기울기 오차 δθ(rad)의 높이 민감도는 수평거리 r에서 대략 `r × δθ`입니다. 예를 들어 10 m에서 0.5°는 약 8.7 cm, 0.1°는 약 1.75 cm의 민감도입니다. 이 예시는 실제 기기의 측정 성능이나 전체 오차 상한이 아니며 깊이·기준점·잔디·조준 오차를 포함하지 않습니다. [NIST 불확도 전파](https://www.nist.gov/pml/nist-technical-note-1297/nist-tn-1297-appendix-law-propagation-uncertainty)

오차가 없는 센서와 좌표라는 이상적 모델에서는 오차 0을 가정할 수 있지만 실제 스마트폰의 보증으로 전환할 수는 없습니다. **현장 검증 없이 현실의 최고 정밀도를 보장하지 않습니다.**

## 5. GPS와 여러 사람의 데이터

GPS는 구장·홀 탐색과 자료를 묶어 찾는 데 사용합니다. 같은 GPS 부근이라는 사실은 같은 cm 단위 지면점이라는 증거가 아닙니다. GPS 고도나 휴대전화 기울기로 잔디의 높낮이를 직접 만들지 않습니다.

Web Geolocation의 accuracy/altitudeAccuracy는 API의 정확도 정보이며 현재 AR 점의 오차가 아닙니다. 없는 고도·정확도 값은 0으로 채우지 않고 이동 heading을 카메라 조준 방향으로 쓰지 않습니다. [W3C Geolocation](https://www.w3.org/TR/geolocation/)

웹 AR 수집은 최초 동의 후 최소 30초 간격·최대 24개 점의 수치 요약입니다. 위치 사용을 허용하고 최근 GPS를 받았을 때만 장소 검색용 위치를 포함하며, 새 원본 사진·영상·전체 깊이맵은 전송하지 않습니다. 따라서 이 요약만으로 다중 사용자 사진측량이나 전체 구장 지형 정합이 이미 동작한다고 해석하지 않습니다. 이전 사진 기록은 해당 시점의 동의와 함께 보존합니다.

공동 지형을 만들려면 공통 기준점·미터 척도·카메라 자세와 중첩된 관측으로 좌표를 정합하고 독립 기준점에서 개선을 확인해야 합니다. 사용자·기기·날짜별 상관과 편향, 정합 오차를 분리하며 보정에 쓴 자료를 평가에 재사용하지 않습니다. 잔디 관리·강우·계절로 달라진 지형은 새 버전으로 구분해야 합니다.

## 6. 보존된 이전 평지 거리 모델

`ground/physics.mjs`는 이전 웹 화면의 조건부 거리 계산을 보존한 모듈입니다. 현재 WebXR 높이·거리 계산의 입력으로 사용하지 않습니다. 평지에서 렌즈 높이 h와 수평선 아래 조준각 α를 알 때:

```text
d = h / tan(α)
최소 거리 = (h − e_h) / tan(α + e_α)
최대 거리 = (h + e_h) / tan(α − e_α)
```

높이 구간 전체가 양수이고 각도 구간이 0° 초과·90° 미만이라는 조건에서 얻는 수학적 극값입니다. 입력 ±범위는 가정한 절대 오차 범위이며 표준편차·RMSE·95% 신뢰구간이 아닙니다. 평지 가정이 틀리거나 입력이 가정 범위를 벗어나면 결과 범위도 성립하지 않습니다. 구현의 `worstCaseM`를 현실의 모든 오차 상한으로 읽으면 안 됩니다.

렌즈 높이 1.20 m ±0.05 m, 조준각 오차 ±1°를 가정한 예시:

| 명목 수평거리 | 조준각 | 조건부 거리 구간 | 최대 편차 |
| --- | --- | --- | --- |
| 2 m | 30.964° | 1.843–2.168 m | 0.168 m |
| 5 m | 13.496° | 4.448–5.640 m | 0.640 m |
| 10 m | 6.843° | 8.349–12.215 m | 2.215 m |

이 표는 실제 기기 성능표가 아니며 현재 WebXR의 정확도 추정치도 아닙니다. 단일 각도 기반 모델에서 먼 지점을 볼수록 입력 오차 민감도가 커지는 이유를 보여 줍니다.

## 7. 실제 검증의 기준

1. 실제 지원 기기의 브라우저에서 깊이 기능 협상, 카메라/깊이 정렬, 자동 기준, 좌우 이동, 추적 상실·복구, 화면 회전과 오래된 값 차단을 확인합니다. 데스크톱 모의 시험으로 대체하지 않습니다.
2. 검증된 거리계·줄자·수준기 등 독립 기준과 비교하고 거리·높이·경사별 signed bias, MAE, RMSE, 95백분위 절대오차를 보고합니다.
3. 기기·거리·빛·잔디·사용자·날짜별 조건을 나누고 실패율·결측률과 표본 수를 함께 제시합니다. 필터 통과 데이터만 골라 성능을 과장하지 않습니다.
4. 추가 사용자 자료가 실제로 오차를 줄이는지 정합에 사용하지 않은 기준점에서 확인합니다. 불확실한 곳은 빈 곳으로 남깁니다.
5. 지형이 용도별 기준을 만족한 후 공 인식·속도·방향과 잔디 구름 저항을 보정하고 실제 궤적과 예측 구간을 비교합니다.

WebXR에는 안전한 출처와 지원 기기·브라우저가 필요하며 Android AR은 ARCore 지원 기기와 Google Play Services for AR에 의존합니다. immersive AR 지원 확인만으로 CPU 깊이 기능까지 보장되지는 않으므로 시작 시 필요한 기능을 협상합니다. [Google WebXR 요구사항](https://developers.google.com/ar/develop/webxr/requirements), [ARCore 깊이 원리](https://developers.google.com/ar/develop/depth), [Apple sceneDepth](https://developer.apple.com/documentation/arkit/displaying-a-point-cloud-using-scene-depth)
